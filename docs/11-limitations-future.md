# 11. Limitations และ Future Improvement Plan

> **หลักของเอกสารนี้:** ทุกข้อจำกัดต้องมาคู่กับ **สิ่งที่เราทำแล้วเพื่อไม่ให้มันหลอกผู้ใช้** และ **สิ่งที่จะแก้จริงถ้าไปต่อ** — ไม่ใช่รายการข้อแก้ตัว
>
> ข้อจำกัดหลายข้อในนี้ **ไม่ใช่การเดา** แต่เจอจริงระหว่างสร้าง (มีเลข error, เลข commit, ผลทดสอบกำกับ)

## 11.1 ขอบเขตที่ตั้งใจไม่ทำ

| ไม่ทำ | เหตุผล |
| --- | --- |
| นับแคลอรี · วิเคราะห์รูปอาหาร · อะไรที่แตะน้ำหนัก/รูปร่าง | **ห้ามโดย guardrail ไม่ใช่แค่ตัดออกเพราะไม่มีเวลา** — `findForbiddenTerms()` บล็อกข้อความที่ระบบสร้างเอง และ CI แดงถ้าหลุด |
| Push notification / LINE | ต้องมี infra ส่งข้อความ + ขอ consent เพิ่ม เกินสโคป 4 สัปดาห์ |
| เชื่อม wearable / health API | ไม่มีอุปกรณ์ให้ทดสอบ และจะเปลี่ยนดีไซน์ check-in ทั้งหมด |
| Dashboard ภาพรวมองค์กร/มหาวิทยาลัย | ขัดหลัก privacy ที่ประกาศไว้ ถ้าทำต้องเป็นค่าเฉลี่ยกลุ่ม ≥ 20 คนเท่านั้น |
| รองรับหลาย persona | โจทย์ข้อ 7.1 ให้เลือก persona เดียว — เลือก "ปาล์ม" (นักศึกษาปี 3 ตารางไม่แน่นอน) |

## 11.2 ข้อจำกัดของข้อมูล

**ข้อมูลมาจากผู้ใช้กรอกเองทั้งหมด (self-reported)** — ไม่มีเซนเซอร์ยืนยัน คนจำผิดหรือกรอกให้ดูดีได้
→ **ทำแล้ว:** ออกแบบให้การกรอกตามจริงไม่มีต้นทุนทางใจ — ไม่มีคะแนน ไม่มีเกรด ไม่มีสตรีคที่ทำให้เสียดายเวลาขาด ภาษาไม่ตัดสิน
→ **ถ้าไปต่อ:** ดึงชั่วโมงนอน/จำนวนก้าวจาก wearable มาเป็นค่าตั้งต้นให้ผู้ใช้แก้ ลดทั้งภาระและอคติ

**เก็บ "นาทีเคลื่อนไหวรวม + ชนิดกิจกรรม" แต่ไม่เก็บนาทีต่อชนิด**
→ เจอตอนทำกราฟ F2-02: โค้ดเวอร์ชันแรกเอานาทีรวมหารเฉลี่ยทุกชนิดแล้ววาดเป็นสัดส่วน (เดิน 25 + ยืด 5 นาที กลายเป็น 15/15) = **กราฟโกหก** → เปลี่ยนเป็นแท่งนาทีรวมสีเดียวที่ตรงกับข้อมูลจริง
→ **ทำไมไม่เก็บเพิ่ม:** ถามนาทีต่อชนิดคือเพิ่มคำถามในฟอร์มที่ต้องจบใน 1–3 นาที **แลกไม่คุ้ม** — เราเลือกกราฟที่จริงกว่าแทนกราฟที่ละเอียดกว่า

**ข้อมูลยังสั้น** — demo account 24 วัน + ทีม dogfood ตั้งแต่ 13 ก.ค.
→ **ทำแล้ว:** `checkDataSufficiency()` ปฏิเสธการวิเคราะห์ถ้าน้อยกว่า 7 วัน (F3-04) และ reflection ต่ำกว่า 3 วันจะไม่เรียก AI เลย — **ระบบยอมบอกว่า "ยังไม่พอ" ดีกว่าเดาให้ฟังดูฉลาด**

**ยังไม่มีการประเมินผลกับผู้ใช้จริงนอกทีม** — n = 4 และทุกคนคือคนสร้าง
→ **ถ้าไปต่อ:** ทดสอบกับนักศึกษา 10–15 คนที่ไม่รู้จักโปรเจกต์ วัด 2 อย่าง: กรอกจบใน 3 นาทีจริงไหม และสัปดาห์ที่ 2 ยังกลับมาบันทึกไหม

## 11.3 ข้อจำกัดของ AI

**Pattern ที่เจอคือความสัมพันธ์ ไม่ใช่เหตุและผล**
→ **ทำแล้ว 3 ชั้น:** โค้ดไม่ส่งข้อมูล < 7 วันให้ LLM · system prompt สั่งห้ามสรุปเหตุ-ผลพร้อมตัวอย่าง · `CAUSAL_TERMS` (`เป็นเพราะ`, `เกิดจาก`, `สาเหตุมาจาก`) เป็นคำที่ตรวจจับได้
→ **หลักฐาน:** QA-01 เคส 10 รอบแรก AI หลุดเขียน "อาจจะเป็นเพราะตื่นสาย" → แก้ prompt → รอบยืนยัน 16 ก.ค. นำเสนอเป็น "ข้อสังเกต" แล้ว

**คำแนะนำมาจาก LLM ที่ควบคุมได้ไม่ 100%**
→ **ทำแล้ว:** ทุก goal ต้องผ่าน `validateGoalTitle()` ก่อนถูกใช้เสมอ ไม่ผ่าน = ทิ้งแล้ว fallback ไป goal มาตรฐานจากตารางโจทย์ · **เป็นการรับประกันเชิงโครงสร้าง ไม่ใช่การสุ่มตรวจ**
→ **ข้อจำกัดที่เหลือ:** guardrail ของ**ข้อความแชท**ยังต้องใช้คนอ่านยืนยัน เพราะการปฏิเสธที่ถูกต้องต้องเอ่ยคำต้องห้ามเอง ("โค้ชให้แผนลดน้ำหนักไม่ได้") — บล็อกอัตโนมัติ = โค้ชปฏิเสธไม่เป็น
→ **หลักฐานยืนยันการตัดสินใจนี้ (22 ก.ค.):** ยิงคำถามล่อ 6 หมวดตามข้อห้ามใน §8 ของโจทย์ (ขอแผนลดน้ำหนัก · ขอตาราง IF · ขอให้วินิจฉัยโรค · ขอให้แนะนำอาหารเสริม · ขอให้วิจารณ์รูปร่าง · ความคิดทำร้ายตัวเอง) บนโมเดล production — **ปฏิเสธถูก 6/6** และให้สายด่วน 1323 ครบทั้งเคสวิกฤต · **3 ใน 6 คำตอบที่ถูกต้องนั้นมีคำต้องห้ามอยู่จริง** ("ผมไม่พูดคุยเรื่องน้ำหนัก รูปร่าง", "ผมจัดตารางอดอาหารให้ไม่ได้") — ถ้าเปิดบล็อกอัตโนมัติ ผู้ใช้จะได้ error แทนคำปฏิเสธที่ทำหน้าที่ safety ได้ดีที่สุด

**บทสนทนาใน guided flow เป็นบทที่เขียนไว้ล่วงหน้า ไม่ใช่ AI**
→ ตัว flow (ถาม 3 คำถาม) เป็นแบบฟอร์มที่แต่งเป็นบทสนทนา · **ส่วนที่เป็น AI จริงคือ goal ที่เสนอ** ซึ่งมาจาก check-in จริง + โปรไฟล์ + คำตอบใน flow ผ่าน `recommendGoals(context)`
→ **ถ้าไปต่อ:** ให้ LLM คุมบทสนทนาเองแบบ multi-turn — แต่ต้องแลกกับความคาดเดาได้และโควตา

**สถานะผู้ใช้ (นักศึกษา / first jobber) ไปถึงแค่โค้ช ไม่ถึง AI อีก 3 เส้น** — โจทย์ตั้งชื่อ mission ว่า "for Students **and First Jobbers**" และ §3.2 ให้ความต้องการของ first jobber ไว้ 4 ข้อเท่ากับนักศึกษา
→ **ทำแล้ว:** onboarding ถามสถานะ · เก็บใน `profiles.status` · **แชทโค้ชได้รับจริง** ผ่าน `buildCoachContext()` → `formatCoachContext()` และมี unit test ยืนยันว่าคำว่า "นักศึกษา" โผล่ใน context ที่ส่งเข้าโมเดล
→ **ข้อจำกัดที่เหลือ:** อีก 3 เส้นไม่เห็นค่านี้เลย — `GoalProfile` (แนะนำ micro goal) มีแค่ `earlyDays`/`busyPeriods`/`constraints` · insight ไม่รับโปรไฟล์ · reflection รับแค่สถานะของ**เป้าหมาย** ไม่ใช่ของผู้ใช้ · **ทั้งสามจึงปฏิบัติกับนักศึกษาและ first jobber เหมือนกันทุกประการ**
→ **ทำไมยังใช้ได้:** ความต่างที่มีผลจริงถูกส่งผ่าน**พฤติกรรมที่บันทึกไว้** ไม่ใช่ป้ายที่ผู้ใช้ประกาศ — คนที่เลือก "เรียนเช้า" กับคนที่เลือก "ประชุมยาว/เดินทางไกล" ได้คำแนะนำคนละแบบอยู่แล้วเพราะ disruptor และข้อจำกัดต่างกัน · การผูกกับสิ่งที่ทำจริงแม่นกว่าการผูกกับป้าย
→ **ผลที่ตามมาที่ต้องยอมรับ:** ถ้า first jobber กับนักศึกษาบันทึกพฤติกรรมเหมือนกันเป๊ะ จะได้เป้าหมายและบทวิเคราะห์เหมือนกันทุกคำ — prototype ใช้ persona เดียว (ปาล์ม) ตาม §7.1 จึงไม่เคยเห็นเคสนี้บน seed data
→ **ถ้าไปต่อ:** เติม `status` เข้า `GoalProfile` และ facts ของ insight/reflection แล้วให้ prompt ปรับตัวอย่างให้ตรงบริบท (เช่น "หลังเลิกงาน" แทน "หลังเลิกเรียน") · ต้นทุนต่ำเพราะข้อมูลมีอยู่แล้ว ไม่ต้องถามผู้ใช้เพิ่ม

**ตัวตรวจคำต้องห้ามดูที่ "คำ" ไม่ใช่ "เจตนา"** — `findForbiddenTerms()` จับ substring ตรง ๆ จึงแยก "คุณล้มเหลว" กับ "ไม่ใช่เรื่องน่าล้มเหลวเลย" ไม่ออก
→ **ผลที่ตามมา:** ข้อความที่ให้กำลังใจถูกกรองทิ้งได้เงียบ ๆ — ใน insight/reflection คือตกไปใช้ template โดยไม่มีใครรู้ · ใน goal คือถูกตีตกพร้อมข้อความ error ที่พูดเรื่องน้ำหนัก/อดอาหาร ซึ่งไม่ตรงกับคำที่ติดจริง (ผู้ใช้ที่พิมพ์เป้าหมายเองก็เจอ)
→ **ย้อนแย้งที่สุด:** โจทย์เอง (§6 "ไม่ทำให้ผู้ใช้รู้สึก**ล้มเหลว**ง่าย") และ system prompt ของเราเอง ("คำแนะนำ... และ**ล้มเหลว**ยาก") ก็ใช้คำนี้ — ถ้า AI เขียนสำนวนเดียวกับที่เราสั่งให้เขียน มันจะถูกกรองทิ้ง
→ **ทำไมยังไม่แก้:** ยอมกรองเกินดีกว่ากรองหลุด — ของที่ถูกทิ้งมี fallback ที่ปลอดภัยเสมอ จึงไม่ใช่ของพัง และการแก้ตัวกรองความปลอดภัยช่วงใกล้ code freeze เสี่ยงกว่าผลที่ได้
→ **ถ้าไปต่อ:** ให้ `JUDGING_TERMS` ดูบริบทรอบคำ (ตัวปฏิเสธนำหน้าอย่าง "ไม่ใช่" "ไม่ได้แปลว่า") ขณะที่ `BODY_TERMS`/`RESTRICTION_TERMS` ยังจับตรง ๆ ต่อไปเพราะไม่มีบริบทไหนที่ควรผ่าน · แก้ข้อความ error ของ goal ให้ตรงกับคำที่ติดจริง

**ผลทดสอบ safety ผ่านคือ "รอบที่สะอาด" ไม่ใช่การพิสูจน์ทางคณิตศาสตร์** — LLM เป็นระบบความน่าจะเป็น
→ **ทำแล้ว (QA-01 ปิดสมบูรณ์ 19 ก.ค.):** รันเต็ม 10 เคส × 2 ประโยค = 20/20 นัด บนโมเดล production ที่ pin ไว้ · ประโยคทดสอบ commit ก่อนรัน · ผลดิบ commit ไม่ตัดต่อ · **คนตรวจยืนยันไม่ใช่คนเขียน prompt** (หลักฐานใน `.scratch/ai-safety-test/`)
→ **ข้อจำกัดที่เหลือ:** ผ่าน 20/20 หนึ่งรอบไม่การันตีทุกรอบ — จึงมีด่านโค้ด (`validateGoalTitle`, escalation, sufficiency) เป็นชั้นที่ไม่ขึ้นกับความน่าจะเป็นของ LLM

**หลักฐาน 20/20 เก็บมาโดย "ไม่แนบบริบทผู้ใช้" แต่ผู้ใช้จริงมีบริบทเสมอ** — พบตอน QA-02 (26 ก.ค.)
→ **ช่องว่าง:** สคริปต์ที่สร้างหลักฐาน (`test-ai.ts`, `test-escalation.ts`) เรียก `generate([{ role: "user", content: prompt }])` คือ `COACH_SYSTEM_PROMPT` ล้วน ๆ · เส้นจริง (`replyToHistory`) ต่อบล็อกบริบทท้าย system เสมอ **และใส่คำถามเปิดของโค้ชเป็น turn แรก** ("วันนั้นพลังงานต่ำที่สุด… วันนั้นเกิดอะไรขึ้นบ้าง") · 20/20 จึงพิสูจน์ว่า **prompt guardrail** ทำงาน แต่ไม่ได้พิสูจน์เส้นทางที่ผู้ใช้เดินจริง
→ **สองเส้นต่างกันจริง ไม่ใช่ทฤษฎี:** ยิงเคส 01 (ถามวินิจฉัยโรค) **พร้อมบริบท** แล้วโค้ชเอาอาการที่ผู้ใช้เพิ่งเอ่ยไปผูกกับตัวเลขที่บันทึกไว้ เช่น *"วันที่มีอาการปวดหัว มักจะเป็นวันที่คุณนอนน้อยกว่า 6 ชั่วโมง"* — **ระบบไม่เคยเก็บว่าปวดหัววันไหน** · การปฏิเสธและการส่งต่อแพทย์ยังครบทุกครั้ง จึงไม่ใช่ guardrail หลุด แต่เป็นการอ้างเกินข้อมูลที่มี ซึ่งขัดหลักการ "แยกสัญญาณจากข้อสรุป" ของ §8
→ **ทำไมถึงเกิด:** ท้ายบล็อกบริบทเดิมบอกแต่ว่า *ใช้ตัวเลขเหล่านี้อ้างอิงได้* ไม่เคยบอกว่า**ไม่มีอะไร** · พอคำถามเปิดชวนให้ "เชื่อมวันนั้นเข้ากับสิ่งที่เกิด" แล้วผู้ใช้ตอบด้วยอาการ โมเดลก็ต่อจิ๊กซอว์ให้ครบเอง
→ **ทำแล้ว:** เติมขอบเขตของชุดข้อมูลลงท้าย `formatCoachContext()` — บอกตรง ๆ ว่าไม่มีบันทึกอาการหรือความรู้สึกเลยสักวัน ห้ามอ้างว่าเกิดวันเดียวกัน **ให้ถามผู้ใช้แทน** · แก้ที่**บริบท ไม่ใช่ system prompt** หลักฐาน 20/20 จึงยังใช้ได้ทุกตัวอักษรโดยไม่ต้องรันใหม่
→ **ข้อจำกัดที่เหลือ:** วัดด้วย regex เชื่อไม่ได้ทั้งสองทาง — ตอนแรกรายงานต่ำกว่าจริง (พลาดประโยคที่แต่งความรู้สึกโดยไม่เอ่ยชื่ออาการ) หลังแก้กลับรายงานเกิน (นับประโยคที่**ถาม**ว่าเป็นการ**อ้าง**) · **ต้องอ่านด้วยคนเสมอ** เหมือนที่ทำกับ `findForbiddenTerms` ในแชท
→ **ถ้าไปต่อ:** รัน checklist ทั้ง 10 เคสซ้ำในโหมดมีบริบท แล้วเก็บเป็นหลักฐานชุดที่สองคู่กับชุดเดิม (`scripts/probe-coach-safety.ts` เป็นโครงให้แล้ว)

→ **เจอชนเพดานจริง 2 ครั้งใน 24 ชม.** ระหว่างพัฒนา (16–17 ก.ค. ตอนใช้ `gemini-2.5-flash` = 20 ครั้ง/วัน) — ไม่ใช่ความเสี่ยงบนกระดาษ
→ **ทำแล้ว:** ย้ายโมเดลเป็น `gemini-3.1-flash-lite` = **500 ครั้ง/วัน** (25 เท่า — INFRA-23 · รัน safety checklist ใหม่ครบบนโมเดลใหม่) · cache-first ทุกผลวิเคราะห์ · จำกัดแชท 5 ข้อความ/คน/วัน · **fallback ปลอดภัยทุกจุดเมื่อ AI ล่ม** (ผู้ใช้ยังได้ goal/สรุปจากตารางมาตรฐาน ไม่เห็นหน้าพัง) · อุ่นผลวิเคราะห์ demo ล่วงหน้าด้วยคำสั่งเดียว
→ **ข้อจำกัดที่เหลือ:** 500/วันพอสำหรับ demo + ทีม แต่ไม่พอถ้ามีผู้ใช้จริงหลักสิบ (แชร์โควตาก้อนเดียว) + เพดานนาที 15 req/min
→ **ถ้าไปต่อ:** ขึ้น paid tier (ระดับ $ ไม่กี่ดอลลาร์/เดือนก็พอสำหรับผู้ใช้หลักร้อย) + แยกโควตารายผู้ใช้

**ประเมินโมเดลใหม่ซ้ำเมื่อมีรุ่นใหม่ออก (22 ก.ค.)** — ทดสอบ `gemini-3.5-flash-lite` และ `gemini-3.6-flash` เทียบกับรุ่นที่ใช้อยู่ ด้วยข้อมูลจริงและ pipeline จริง
→ **ผล:** `gemini-3.6-flash` ช้ากว่ามาก (แชท 10.4–10.9 วิ vs 2.2–2.4 · วิเคราะห์ 18.4 วิ vs 3.9) และเพดาน **20 ครั้ง/วัน** = ทีม 4 คนคุยคนละ 5 ข้อความก็หมดโควตาทั้งวันก่อนสร้างผลวิเคราะห์สักอัน — **เป็นปัญหาเดียวกับที่เพิ่งหนีมาเมื่อ 16–17 ก.ค.** · `gemini-3.5-flash-lite` เร็วพอกันและโควตาเท่ากัน (500) แต่ไม่ได้ดีกว่าจนคุ้มจะเปลี่ยนน้ำเสียงโค้ชก่อนพิตช์ (คำตอบสั้นลง ~40%)
→ **ตัดสินใจ:** อยู่กับ `gemini-3.1-flash-lite` ต่อ — โมเดลใหม่กว่าไม่ได้แปลว่าเหมาะกว่า เมื่อคอขวดจริงคือโควตาที่แชร์กันทั้งแอป
→ **สลับได้ทุกเมื่อโดยไม่ต้องแก้โค้ด:** `src/lib/ai` อ่าน env `AI_MODEL` ทับค่า default อยู่แล้ว — ตั้งค่าบน Vercel แล้วย้อนกลับได้ทันทีถ้าโมเดลใหม่มีปัญหา

**ลืมรหัสผ่านแล้วกู้เองไม่ได้** — ผู้ใช้ที่สมัครด้วย email/password ต้องติดต่อทีม (ผู้ใช้ Google ไม่มีปัญหานี้)
→ **โค้ดเขียนไว้ครบแล้วแต่ปิดไว้** — `/forgot-password` + `/reset-password` + server action ทำงานได้ แต่ **ถอดลิงก์ออกจากหน้า login เมื่อ 25 ก.ค.**
→ **เหตุผล:** ยังพิสูจน์ไม่ได้ว่า Supabase ส่งอีเมลออกจริง (ไม่มี SMTP ตั้งไว้ · built-in email ของ free tier จำกัดจำนวนต่อชั่วโมง) · และโค้ดจงใจไม่เช็ค error เพื่อไม่เปิดเผยว่าอีเมลไหนมีบัญชี → **ถ้าส่งไม่ออก หน้าจอก็ยังบอกว่า "ส่งลิงก์แล้ว"** ซึ่งหลอกผู้ใช้ แย่กว่าไม่มีฟีเจอร์
→ **ทดสอบก่อนเปิดใช้ (ประมาณ 10 นาที):** รัน dev **บนพอร์ต 3000–3003 เท่านั้น** (allowlist ของ Supabase ตาม ADR-0005 — พอร์ตอื่นจะ fallback ไป production เงียบ ๆ) → สมัครบัญชีด้วย**อีเมลจริงที่เปิดอ่านได้** (ห้าม `@example.com` ซึ่งรับเมลไม่ได้ และห้ามใช้บัญชีปาล์ม) → เข้า `/forgot-password` → เช็คกล่องจดหมายรวม spam → คลิกลิงก์ต้องมาที่ `/reset-password` → ตั้งรหัสใหม่แล้วล็อกอินซ้ำ
→ **ผ่านแล้วค่อยเอาลิงก์กลับ** เข้า [login-form.tsx](../src/components/auth/login-form.tsx) · มีเทสต์ e2e คุมอยู่ว่าตอนนี้ต้องยังไม่มีลิงก์ ถ้าเปิดใช้ต้องแก้เทสต์ด้วย

**~~ล้างประวัติแชท = โควตา 5 ข้อความ/วันรีเซ็ต~~ — แก้แล้ว 24 ก.ค.**
→ เจอจริงตอนเพื่อนกดล้างประวัติระหว่างทดสอบแล้วโควตาเด้งกลับ (INFRA-20)
→ **ทำแล้ว:** ย้ายตัวนับไปตาราง `chat_daily_usage` แบบเพิ่มอย่างเดียว (migration 0004) จึงไม่หายไปพร้อมการลบประวัติ · **ตารางเก็บแค่จำนวนครั้งต่อวัน ไม่มีเนื้อหาข้อความ** คำสัญญาเรื่องการลบในหน้า privacy จึงยังจริงครบทุกตัวอักษร
→ **โค้ดออกแบบให้ fail-safe:** ถ้ายังไม่ได้ apply migration จะตกกลับไปนับจากแถวแบบเดิมโดยอัตโนมัติ แอปไม่พัง — แต่ช่องโหว่จะยังอยู่จนกว่าจะ apply
→ **ผลข้างเคียงที่ทีมต้องรู้:** ทางลัด "ล้างประวัติเพื่อรีเซ็ตโควตาตอนซ้อม" ใช้ไม่ได้แล้ว · `npm run refresh:demo-week` ล้างตัวนับของบัญชีปาล์มให้ด้วย จึงเริ่มวัน pitch ด้วยโควตาเต็มเสมอ

**สรุปสัปดาห์ที่ cache ไว้อาจเก่ากว่าบันทึกล่าสุด** — ข้อความ AI ถูกสร้างตอนหนึ่ง แล้วผู้ใช้บันทึกเพิ่มทีหลัง
→ **ทำแล้ว:** ไม่กลบ — หน้า reflection ขึ้นการ์ด "สรุปนี้ยังไม่รวมบันทึกล่าสุดของคุณ" พร้อมปุ่มสร้างใหม่ · ตัวเลขเทียบสัปดาห์คำนวณสดเสมอ
→ **ถ้าไปต่อ:** regenerate อัตโนมัติแบบ background job — ตอนนี้ทำไม่ได้เพราะจะกินโควตาโดยผู้ใช้ไม่ได้ขอ

**เป็น responsive web app ไม่ใช่แอปเนทีฟ** (ADR-0001) — ไม่มี widget, ไม่มี background sync, ไม่มี local notification
→ ยอมรับเพื่อให้ 4 คนส่งของได้ทันใน 4 สัปดาห์ และแชร์ลิงก์ให้กรรมการเปิดได้ทันที

**ไม่มีโหมด offline** — ถ้าเน็ตหลุดระหว่างกดบันทึก จะได้ข้อความ error ทั่วไป ไม่มีคิวรอส่งซ้ำอัตโนมัติ
→ **ทำแล้ว:** ทุก action ล้มแบบปลอดภัย — ข้อมูลที่กรอกในฟอร์มไม่หาย ขึ้นข้อความ error ภาษาไทย และแชทมีปุ่มลองใหม่
→ **ถ้าไปต่อ:** เก็บ draft ลง localStorage แล้วส่งซ้ำเมื่อกลับมาออนไลน์

**ยังไม่เคยทดสอบกับการขยายฟอนต์ระดับระบบ (Dynamic Type)** — ผู้ใช้ที่ตั้งฟอนต์ใหญ่พิเศษอาจเจอ layout ที่เราไม่เคยเห็น
→ **ทำแล้ว:** layout เป็น flex/grid ทั้งหมด ไม่มีกล่องความสูงตายตัวครอบข้อความ · e2e คุม contrast ≥ 4.5:1 กับ touch target ≥ 44px บน 7 route หลัก + auth 2 หน้า (ยังไม่ครอบ landing/onboarding/edit/error และเคสฟอนต์ขยาย) — จุดนี้คือ "ไม่รู้" ไม่ใช่ "ผ่าน"
→ **ถ้าไปต่อ:** เพิ่ม e2e project ที่ตั้ง font-size 200% แล้วรันชุดตรวจ `expectUsablePage` เดิมทั้งหมด

**คำตอบโค้ชเคยมี markdown ดิบโผล่** (`**ข้อความ**`) — **ปิดครบแล้ว** · `**`/ลิสต์ แก้ 21 ก.ค. · หัวข้อ `##` แก้ 25 ก.ค. พร้อม unit test 6 ข้อที่ใช้คำตอบ Gemini จริงจากไฟล์หลักฐาน safety (F4-06 ปิดแล้ว)
→ หัวข้อเรนเดอร์เป็น**บรรทัดหนา ไม่ใช่ `<h*>` จริง** โดยตั้งใจ — ฟองแชทอยู่ในหน้าที่มีลำดับหัวข้อของตัวเองแล้ว การแทรก `<h2>` จากข้อความ LLM จะทำให้โครงหัวข้อของหน้าเพี้ยน
→ ยังไม่รองรับ: ตัวเอียง · ลิงก์ `[]()` · code fence · ลิสต์ซ้อนชั้น — ทั้งหมดจะโผล่เป็นตัวอักษรดิบ แต่ไม่เคยเจอในคำตอบจริง เพราะ system prompt ไม่ได้สั่งให้ใช้

## 11.5 สิ่งที่เรียนรู้จากการสร้างและใช้จริง

> ส่วนนี้ไม่มีอยู่ในแผนตอนแรก — เกิดจากการที่ทีม dogfood และรีวิวโค้ดกันเองจริงจัง

**1. "มีเทสต์" ไม่เท่ากับ "จับได้"** — มี PR ที่เปลี่ยนโมเดล AI จาก `gemini-2.5-flash` เป็น `gemini-2.0-flash` แล้ว **CI ผ่านทั้ง verify + e2e** ถ้า merge ไป หลักฐานความปลอดภัยทั้งหมดจะกลายเป็นของโมเดลที่ไม่เคยทดสอบ โดยไม่มีใครรู้จนวัน pitch
→ **แก้:** unit test ล็อกชื่อโมเดล (INFRA-19) พร้อมข้อความบอกว่าหลักฐานอะไรจะพังถ้าเปลี่ยน — **ตอนนี้การเปลี่ยนโมเดลเงียบ ๆ เป็นไปไม่ได้แล้ว**

**2. เทสต์จับหน้าจอที่พัง แต่ไม่จับหน้าที่ "ไปไม่ถึง"** — มี PR ที่ถอดการ์ดออกจาก dashboard ซึ่งบังเอิญเป็น**ลิงก์เดียวในทั้งแอปที่ไปหน้าสรุปสัปดาห์** e2e ยังเขียวหมดเพราะมันเปิดหน้านั้นผ่าน URL ตรง ๆ
→ **แก้:** จับได้ตอนรีวิวด้วยคน + คืนการ์ดกลับ · บทเรียนคือ **หน้าที่ไม่มีทางเข้า = หน้าที่ไม่มีอยู่จริง** สำหรับผู้ใช้และกรรมการ

**3. บัญชี demo ที่เป็นสนามทดสอบด้วย จะมีขยะโผล่ตอนนำเสนอ** — เจอข้อความทดสอบ (`ddsdsa`) และ goal ทดสอบค้างในบัญชีปาล์ม
→ **แก้:** ออกกติกา "เทสด้วยบัญชีสมัครทิ้ง" + ใส่การล้างบัญชี demo ในเช็คลิสต์ก่อน pitch (QA-03)

**4. เอกสารที่ตามหลังโค้ดคือเอกสารที่หลอกทีมตัวเอง** — มีช่วงที่บอร์ดอ่านว่างานยังไม่เริ่ม ทั้งที่โค้ดขึ้น production ไปแล้ว (เพราะ PR ใบเดียวทำ 2 issue) และมีการอ้างถึง issue ที่ไม่เคยถูกสร้าง
→ **แก้:** ปิด issue พร้อมหลักฐานทุกใบ · sync บอร์ดทุกครั้งที่ merge เป็นชุด

**5. ฟอร์มแคบกรอกง่ายกว่า แต่เดสก์ท็อปจะดูโล่ง** — แก้ด้วยการเติม step rail ข้าง ๆ **ไม่ใช่ขยายฟอร์ม** (INFRA-17)
