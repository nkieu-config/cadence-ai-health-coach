# INFRA-20: ล้างประวัติแชท = โควตารีเซ็ตฟรี

Status: done
Owner: A

Priority: S — กันโควตาทีมหมดคาวัน pitch
Refs: INFRA-07, F4-05, ADR-0003

## ปัญหา

`countMessagesToday()` นับ**แถวใน `chat_messages`** ของวันนี้เพื่อบังคับเพดาน 5 ข้อความ/คน/วัน · แต่ `clearChatHistory()` (F4-05) ลบแถวจริง → **กดล้างประวัติ = ได้โควตา 5 ใหม่ทันที ไม่จำกัดรอบ**

ไม่ใช่ทฤษฎี — เกิดจริงเมื่อ 16 ก.ค. เวลา 11:09 คีตะกดล้างประวัติระหว่างทดสอบ แล้วโควตาเด้งจาก 2 กลับเป็น 5 โดยไม่ได้ตั้งใจ

เพดาน 5/วัน มีไว้กันโควตา Gemini ฟรีของทั้งแอป (ADR-0003) ไม่ใช่กันผู้ใช้ — ถ้าทะลุได้ วัน pitch อาจโดนใครเผลอยิงจนหมดก่อนขึ้นเวที

> **อัปเดต 20 ก.ค.:** หลัง INFRA-23 โควตาเป็น **500 ครั้ง/วัน** (เดิม 20) → ความเร่งด่วนลดลงมาก · ช่องโหว่ยังอยู่จริงและควรแก้ แต่**ไม่ใช่ความเสี่ยงระดับล้ม demo แล้ว** — ถ้าไม่ทันก่อน freeze ให้บันทึกใน docs/11 ตามหมายเหตุท้ายไฟล์

## งาน

- [x] แยกตัวนับออกจากตารางที่ลบได้ — เช่น ตาราง `chat_usage (user_id, day, count)` นับเพิ่มตอนส่งจริง ไม่ผูกกับการมีอยู่ของข้อความ
- [x] `clearChatHistory()` ต้องไม่แตะตัวนับ — ลบประวัติได้ แต่โควตาวันนั้นไม่คืน
- [x] ผู้ใช้ยังลบข้อมูลตัวเองได้ครบตามเกณฑ์ Privacy (F7-02 `deleteAllData` ต้องล้างตัวนับด้วย — ลบบัญชี/ข้อมูลทั้งหมดคือคนละเรื่องกับล้างแชทเพื่อขอโควตา)
- [x] RLS: ผู้ใช้อ่านของตัวเองได้ แต่แก้ตัวนับเองไม่ได้

## Acceptance criteria

- ส่ง 5 ข้อความ → ล้างประวัติ → ส่งอีก 1 = **ถูกปฏิเสธ** (ทดสอบด้วยบัญชีสมัครทิ้ง ไม่ยิง Gemini เกินจำเป็น)
- `deleteAllData()` แล้วโควตาคืน (ผู้ใช้เริ่มต้นใหม่จริง ๆ)
- `messagesLeftToday()` signature เดิม — 🟩 ไม่ต้องแก้ UI

25 ก.ค. (A) — **โค้ดครบแล้ว รอ apply migration 0005 ก่อนจึงปิดได้**

รอบแรก (migration 0004) ปิดได้แค่ 2 จาก 4 AC · ตรวจซ้ำแล้วพบว่า:

- **`deleteAllData()` ไม่ล้างตัวนับ** — `USER_DATA_TABLES` มี 5 ตาราง ไม่รวม `chat_daily_usage` · ผู้ใช้กด "ลบข้อมูลทั้งหมด" แล้วยังเหลือแถวผูก `user_id` ค้างในระบบ (ลบ**บัญชี**ล้างครบเพราะมี `on delete cascade` — เฉพาะ "ลบข้อมูล" ที่ไม่ครบ)
- **policy เดิมเป็น `for all`** — ผู้ใช้ `update`/`delete` แถวตัวนับตัวเองได้ · ยิงตรงเข้า Supabase ด้วย JWT ตัวเองแล้วล้างประวัติซ้ำ = **ช่องโหว่เดิมกลับมาทั้งดุ้น** เพราะ `countMessagesToday()` คืน `max(ตัวนับ, จำนวนแถว)` ซึ่งกลายเป็น 0 ทั้งคู่

สองข้อนี้แก้แยกกันไม่ได้ — ถ้าห้ามผู้ใช้เขียนตาราง `bump_chat_usage` ที่เป็น `security invoker` จะพังตาม และ `deleteAllData()` ก็ลบไม่ได้

**migration 0005** จึงทำสามอย่างพร้อมกัน: policy เหลือ `for select` · `bump_chat_usage` เป็น `security definer` (บังคับ `auth.uid()` ในตัว แตะของคนอื่นไม่ได้) · เพิ่ม `clear_chat_usage()` ให้ `deleteAllData()` เรียก · ทั้งคู่ `set search_path = public` และ revoke จาก `public` เหลือ grant ให้ `authenticated`

เอกสารที่ตามมาด้วย: `docs/05` เพิ่ม DDL + migration 0004/0005 · `docs/08` และหน้า `/settings/privacy` เพิ่มแถว "จำนวนข้อความที่คุยกับ coach ในแต่ละวัน" ในตารางว่าเก็บอะไร (โจทย์ §9 ถามตรง ๆ ว่าระบบเก็บอะไรบ้าง)

⚠️ **ห้าม deploy ก่อน apply 0005** — `deleteAllData()` เรียก RPC `clear_chat_usage` ถ้ายังไม่มีจะคืน error แล้วปุ่ม "ลบข้อมูลทั้งหมด" พังทั้งที่เดิมทำงานได้

25 ก.ค. (A) — **ปิดแล้ว · migration 0005 ลง production เรียบร้อย แล้ว push โค้ดตาม**

ยิงในนามผู้ใช้จริง (JWT ของบัญชีเทส ไม่ใช่ service role) แล้วได้ครบทั้ง 4 ทาง:

| ยิงอะไร | ผล |
|---|---|
| `bump_chat_usage` | คืนค่า 1 — ตัวนับยังเพิ่มได้ตามปกติ |
| `select` ตาราง | เห็นเฉพาะแถวตัวเอง |
| `delete` แถวตัวเอง | **0 แถวถูกลบ** |
| `update` ตัวนับเป็น 0 | **0 แถวถูกแก้** |
| `clear_chat_usage` | ล้างได้ เหลือ 0 แถว |

AC ข้อ "`deleteAllData()` แล้วโควตาคืน" ยืนยันบนของจริงระหว่าง QA-02 ด้วย — กดปุ่ม "ลบข้อมูลทั้งหมด" จากหน้าเว็บแล้วนับแถวในฐานข้อมูล **ทั้ง 6 ตารางเหลือ 0 รวม `chat_daily_usage`**

AC ข้อ "ส่ง 5 ข้อความ → ล้างประวัติ → ส่งอีก 1 ถูกปฏิเสธ" ไม่ได้เดินซ้ำ เพราะหลัง INFRA-23 เพดานเป็น 500/วัน การยิงให้ถึงเพดานสิ้นเปลืองโควตาโดยไม่จำเป็น — สิ่งที่ AC ข้อนี้กันคือ "ล้างประวัติแล้วตัวนับกลับเป็นศูนย์" ซึ่งตอนนี้ปิดที่ระดับ RLS แล้วว่าผู้ใช้แตะตัวนับไม่ได้เลย ไม่ว่าจะผ่าน UI หรือยิงตรง
